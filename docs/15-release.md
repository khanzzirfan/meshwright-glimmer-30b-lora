## 4. Spec: `v1-gguf`, the cross-platform tag (free, local)

**Why.** `:v1` runs only on Apple Silicon. Ollama's library has portable builds of the same model:
`muse-glimmer:30b` (= `30b-q4_K_M`, 16.8 GB model + 1.4 GB vision projector), `30b-q8_0` and `30b-bf16`
(registry checked 22 Nov 2026). A tag built on `muse-glimmer:30b` runs on Linux, Windows, NVIDIA and CPU.

**Build.** Same system prompt and parameters as v1, only `FROM muse-glimmer:30b`. The Modelfile is generated by
`scripts/release_modelfile.py` (rel-1 US-001), never hand-edited, so the two tags cannot drift.

**Gate before pushing** (different quantisation from what we measured, so check it):
- Run the 12 dev briefs (`bench/glb/dev_briefs.jsonl`) single-sample through the new tag on the Mac with the
  `meshwright-v1-gguf` model row (rel-1 US-002) and validate.
- Push only if valid >= 10/12 and assembled-of-valid within 15 points of the `:v1` tag on the same 12 briefs
  (run `:v1` the same way for the comparison). Otherwise do not push; record the numbers here.
- Record seconds per brief. On the Mac the GGUF build is expected to be slower than MLX (not measured).

**Publish.** `ollama push khanzz_irfan/meshwright-glimmer-30b-lora:v1-gguf` (owner session, after the gate),
then add the tag to the HF card's quick start with one line on which to pick.

**Ops.** `bash scripts/rel_ops.sh start gguf-dev` and `... status` (rel-1 US-004) pull the base, create the
tag, run both 12-brief rows and write `runs/rel/gguf_dev.md`. The push is never in the script.

## 5. Spec: v2, the first trained weights (paid, needs approval)

**Goal.** A LoRA on the GLB track that makes single samples better, so `ollama run` gets closer to the
generator without best-of-N.

**Data.** `runs/imp/distill_data` (423 train after removing x0114, 39 val, answer-only rows, v3 system prompt). Not ccore's data
(its generator's terms are unchecked).

**Train** (rented GPU, owner approval and a dollar cap each time):
1. 20-step smoke run to measure seconds per step, then `glb_phase2_estimate.py` gives the full cost.
2. Full run: `scripts/mesh_lora_hf.py --data runs/imp/distill_data` (BF16 LoRA, rank 16, lr 1e-4, 2 epochs,
   106 steps). Keep the epoch with the lowest validation loss.
3. Download the adapter and loss curve; stop and delete the pod.
`scripts/v2_pod.sh` (rel-1 US-005) prints this runbook as commands and refuses to create anything without
`--approve-spend --max-usd N`. Estimated A100 80 GB time is a few hours (estimate; not measured).

**Export (VERIFY, untested for Glimmer).** Options, in order of preference:
1. Ollama `ADAPTER` line in a Modelfile over the base (works only if Ollama supports adapters for the
   `muse_glimmer` architecture).
2. Merge on the pod (`peft merge_and_unload`), then `ollama create --quantize q4_K_M` from the merged
   safetensors directory, or llama.cpp `convert_hf_to_gguf.py` + `llama-quantize`.
3. MLX: `mlx_lm fuse`; the earlier MLX convert failed on the `model.vision_*` key prefix (HANDOVER), so patch
   or strip those keys first.
The Mac has about 96 GB free; the BF16 base (58 GB) is no longer cached, so do the merge and quantise on the pod
and download only the quantised result.

**Release gate** (`scripts/release_compare.py`, rel-1 US-006). v2 replaces v1 as the recommended tag only if, on
the 48 eval briefs, single sample:
- valid rate >= v1's,
- assembled (of all briefs) >= v1's + 10 points,
- and, once the owner has blind-rated both, good rate (rated 2) >= v1's.
Otherwise v2 is not published, or is published as experimental. Seconds per brief are reported, not gated.

**Publish.** Adapter files and the merged/quantised build go to the same HF repo (new card section "v2"), the
Ollama tag `:v2` (and `:v2-gguf` if the export allows), a `v2` git tag, and "Fine-tuned from Muse Glimmer 30B"
on the card. The v1 section stays.

### Studio renders (`scripts/showcase_render.mjs`)

`scripts/showcase_render.mjs` renders each exported GLB as a transparent-background 3/4 studio shot (soft key
light, rim light, contact shadow on an invisible ground) into `--out/<name>.png`; `--frames N` also writes a
turntable under `<name>_turn/`. Hero shots add a plinth:

```bash
node scripts/showcase_render.mjs --glb a.glb,b.glb --out DIR [--size 1024] [--frames 0] [--yaw 35] [--pitch 22] \
  [--plinth none|round|square] [--plinth-color 0x9ccf7a] [--plinth-side 0x8a5a3c] [--aspect W:H] [--offset-x F]
```

- `--plinth none|round|square` (default `none`) drops the asset onto a low diorama slab like ccore's hero shots:
  a bevelled base (`--plinth-side`, default `0x8a5a3c`) with a thin top layer (`--plinth-color`, default
  `0x9ccf7a`), sized 1.25x the asset's footprint (its x/z extent), 6% thick, its top surface at y = 0, receiving
  shadows. The camera then frames asset plus plinth (for `none` it frames the asset, as before).
- `--aspect W:H` (default `1:1`) renders at `--size` wide by `size*H/W` tall, so a hero reads 16:9 with
  `--size 1920 --aspect 16:9`. `--offset-x F` (default `0`) shifts the subject F frame-widths to the right.
- With `--plinth none`, `--aspect 1:1` and `--offset-x 0` the output is byte-identical to before these flags
  (`tests/js/showcase_render.test.mjs` asserts it).

### Diorama scenes (`scripts/showcase_scene.mjs`)

`scripts/showcase_scene.mjs` places many exported GLBs on one plinth and renders the group as a single diorama
(ccore's game GIF of assets working together). Geometry, materials and animation are never edited: an asset is
only translated, rotated and uniformly scaled as a whole. The renderer settings, the lights, the contact shadow
and the plinth live in `scripts/showcase_common.mjs`, which both this script and `showcase_render.mjs` serve to
their page, so the studio look is defined once.

The layout JSON is `{plinth: {shape: "round"|"square", size_m, top, side}, camera: {yaw, pitch, fov, zoom},
items: [{glb, x, z, rot_y_deg, height_m?, scale?, on_water?}], water?}`:

- Each item is loaded and placed whole: its lowest point sits on the plinth top (`y = 0`) and its x/z centre moves
  to `(x, z)`. `height_m` scales it uniformly to that real height, otherwise `scale` (default `1`, the asset's own
  metres) applies. An item with `on_water: true` sits on the water surface instead of the land (see below).
- `plinth.size_m` is the round diameter / square side in metres; `top` and `side` are the thin top-layer and body
  colours (defaults `0x9ccf7a` and `0x8a5a3c`). `camera` defaults to `{yaw: 35, pitch: 22, fov: 30, zoom: 1}`.
- Optional `water: {color, side, drop_m}` makes one half of a square plinth a harbour's water (a square is
  required): the plinth top is drawn in `color` (default `0x5aa0d8`) and lowered by `drop_m` (default `0.01` m, so
  the water surface sits 1 cm below the land), and a land shelf in the plinth `top` colour covers the other half.
  `side` is which half is water: `front` (+z, toward the camera) | `back` (-z) | `left` (-x) | `right` (+x).
  `on_water` items then rest on the lowered surface.
- Before rendering it prints a warning line per overlapping pair of x/z footprints (ids and overlap area);
  `--strict` turns any overlap into an error (nothing is rendered). A missing GLB is an error naming the path.
  One JSON line `{items, overlaps, missing}` is always printed last.
- It writes `DIR/NAME.png` (a transparent-background still at `--width` x `--height`); with `--frames N` it also
  writes `DIR/NAME_orbit/0000.png…`, a full 360-degree camera orbit around the plinth centre, playing each
  animated item's first clip.

The two launch dioramas are `release/v1/promo/scenes/village.json` (6 buildings, 5 nature, 5 props, 3 people and
2 animals on a 62 m round plinth; 21 items) and `release/v1/promo/scenes/harbour.json` (a lighthouse, pier,
boathouse and beach hut on a 56 m square plinth's land half, with the trawler, tugboat, sailboat and life raft on
its front water half; 14 items). Rendered 1920x1080 with a 96-frame orbit into `release/v1/promo/scenes_out/`:
`village.png` + `village_orbit/`, `harbour.png` + `harbour_orbit/` and `summary.json` (each scene's ids, 0
overlaps, and the per-item `height_m` scale notes). Geometry is never edited.

```bash
node scripts/showcase_scene.mjs --layout release/v1/promo/scenes/village.json --out DIR \
  [--width 1920] [--height 1080] [--frames 0] [--name village] [--strict]
```

### Hero slides (`release/v1/promo/make.mjs --slides`)

`--slides` switches the promo composer to 16:9 film-style hero slides: one rich subject per slide with a short
headline (ccore's "A world. Of details." slide, in our dark style). A plain run (`make.mjs`) still writes the four
published pages byte-identically; `--slides` writes **only** the slides, so the published `out/` images are never
rewritten.

It reads `release/v1/promo/slides.json`, a list of `{name, kicker, line1, line2, sub, prompt?, image, caption?}`:

- One 1920x1080 slide per entry, written to `out/slides/NN_<name>.png`. The left column has the uppercase kicker
  chip (`#9fb3ff` on a dark pill), `line1` in white and `line2` in accent `#8fd3ff` (both 92px bold), a short rule,
  `sub`, then `prompt` in quotes when given. The trimmed image sits on the right with a drop shadow and the optional
  `caption` in small grey under it. A slide counter `NN / TT` sits top right and `Meshwright v1` bottom right.
- `image` is resolved next to the slides file (an absolute path is used as is). Images from `renders_hero/` and
  `scenes_out/` are trimmed to their content, the way a plain run trims `renders/`.
- `--slides-file FILE` (default `release/v1/promo/slides.json`) and `--out DIR` (default
  `release/v1/promo/out/slides`) override the input and output; a missing or empty slides file exits 2.
- The six slides are `01_world`, `02_market`, `03_farmhouse`, `04_walker`, `05_octopus`, `06_harbour`: the two
  diorama stills (`scenes_out/village.png`, `scenes_out/harbour.png`, captioned "Arranged by hand. Every object
  generated by Meshwright v1.") and four single assets (`g012`, `x0022`, `x0422`, `x0110`), each showing its exact
  prompt from `meta.json`. Headlines carry no number (no quality claim on a slide).

The four asset images are rendered once with the studio plinth before the slides are composed:

### Launch film (`scripts/promo_film.sh`)

`scripts/promo_film.sh` strings the launch material into one 25-30 s 1920x1080 MP4 (H.264, `yuv420p`, CRF 18,
`+faststart`, no audio track) and a 1080x1080 centre-cropped square, using ffmpeg only:

```bash
bash scripts/promo_film.sh [--dry-run] [--promo DIR] [--out DIR]
```

Nine parts, in order, joined by 0.4 s crossfades (eight cuts): title card (`out/cover_1280x640.png` scaled and
padded, 2.5 s) -> village orbit (`scenes_out/village_orbit/`'s `%04d.png` frames at 20 fps, looped to 6 s,
composited over the gradient) -> slides 2-5 (`out/slides/02_market` … `05_octopus`, 2.5 s each with a slow 4%
zoom-in) -> harbour orbit -> `out/turntable_1200.mp4` centred on the gradient (3 s) -> end card (3 s). It writes
`out/film/meshwright_v1_film.mp4` and `out/film/meshwright_v1_film_square.mp4`, prints both ffprobe durations and
exits non-zero when the film falls outside 25-30 s.

Two still cards are prepared once (kept if already present): the dark studio background `bg_1920x1080.png` (an
ffmpeg radial gradient, so the transparent orbit frames composite onto something) and the end card
`out/film/end_card.png` — slide 1's diorama with the headline replaced by the install command and
`Free and open · Apache 2.0 · Built on Muse Glimmer 30B`. The end card is rendered by
`node release/v1/promo/make.mjs --endcard [--out DIR]` (writes `DIR/end_card.png`, default `out/film/`; the
Homebrew ffmpeg has no `drawtext`/libass, so the text is drawn by the Chromium composer instead).

`--dry-run` prints every command line (the ffmpeg gradient, the `make.mjs --endcard` call and each ffmpeg part
and assemble step) without running any of them; `--promo DIR` sets the asset root (default `release/v1/promo`)
and `--out DIR` the output dir (default `DIR/out/film`). `tests/py/test_promo_film.py` runs `--dry-run` against a
temp tree of dummy PNGs and asserts the part order, the eight 0.4 s crossfades and that no network URL appears.

### Blender import check (`scripts/blender_import_check.py`)

`scripts/blender_import_check.py` is the "works in a real tool" proof (Blender 4+ is installed; Godot is not): it
runs headless inside Blender, imports each GLB and reports what loaded. It is launched with the Blender binary, so
its own flags come after `--`:

```bash
blender -b --factory-startup --python scripts/blender_import_check.py -- \
  --glbs a.glb,b.glb --report release/v1/promo/out/blender/report.json \
  --render release/v1/promo/out/blender/blender_village_eevee.png \
  --layout release/v1/promo/scenes/village.json
```

- For every GLB it resets to an empty scene, imports it with `bpy.ops.import_scene.gltf` and records `ok` plus the
  object, mesh, evaluated-triangle, material and action (animation) counts; `--report FILE` gets one row per GLB
  and the totals. Each GLB is imported in **its own Blender subprocess** from a **name-safe temp copy** made by
  `scripts/glb_names.mjs` (names only, geometry untouched), so a GLB whose node names would make Blender 5.2 abort
  still imports; the row carries `raw_names_crash_risk` (`true` when that sanitizer had to rename something in the
  raw GLB). A GLB that still makes Blender abort becomes an `ok: false` row naming the signal, and an import the
  importer itself rejects becomes an `ok: false` row with its message — every GLB is reported, never hidden. Any
  worker Blender still alive when the run ends is killed. The command exits `1` when any GLB failed.
- `--render FILE` also composes `--layout` (placement, plinth, sun and camera follow `showcase_scene.mjs`: the item's
  lowest point sits on the plinth top, its x/z centre at the item's x/z, `height_m`/`scale` and a Y rotation, water
  items lowered by `drop_m`; the camera aims the way `yaw`/`pitch` say with the layout `fov`/`zoom`). It writes the
  EEVEE image to `FILE` and a second Workbench "random colours" parts pass to `--render-parts FILE` (default: the
  `eevee` in `FILE` replaced by `parts`). `--width`/`--height` default to 1920x1080. The render imports its items
  from a name-safe copy too, so the picture is still produced.
- Offline and deterministic. `tests/py/test_blender_import_check.py` checks the offline helpers (the parser, the
  parts-image name, `sanitize_glb_copy`, and the crashed-worker row) with no Blender, then runs the script on a tiny
  GLB written by the test (two boxes, one animation) and asserts `ok`, two meshes, one action and
  `raw_names_crash_risk`; the Blender tests are skipped only when `blender` is not on `PATH`.

Run over all 36 GLBs used by the two dioramas and the six slides, the report is **35 ok, 1 failed** (66,836
triangles). The two GLBs whose node names would abort Blender 5.2 (`runs/imp/distill/x0158/asset.glb`,
`runs/imp/distill/x0149/asset.glb`) import from the name-safe copy and are flagged `raw_names_crash_risk: true`;
`runs/imp/adaptive/best/glimmer-v3-adaptive/glb/g012.glb` has `null` entries in a node `matrix`, which Blender
rejects as invalid glTF (three.js tolerates it and it renders in the hero slides), so that one is a tool-side
limitation, recorded as-is. Outputs: `report.json`, `blender_village_eevee.png` and `blender_village_parts.png`
under `release/v1/promo/out/blender/`.

### Known issue: Blender 5.2 crash on float-suffixed names

Blender 5.2 parses a name that ends in `.<digits>` as a duplicate-number suffix and runs `std::stoi` on the digit
run; on a long fractional coordinate (`bed_plank_0.09999999999999998`) that overflows (`out_of_range`) and Blender
aborts (`SIGABRT`), so the GLB looks broken even though three.js loads it. Measured on the 540 self-distillation
GLBs, **15 abort Blender 5.2**, every one with a long fractional *suffix* (`x0025`, `x0131`, `x0148`, `x0149`,
`x0158`, `x0198` and nine more). A long decimal in the *middle* of a name
(`wall_block_-3.5999999999999996_0`, `x0020`) imports fine and is left alone, because Blender only parses the
name's ending.

`scripts/glb_names.mjs` fixes names at export time. It rounds a name-final decimal to at most 3 fractional digits
(`sack_0.5_1.0499999999999998` -> `sack_0.5_1.05`), turns a name ending in `.<digits>` whose value exceeds 999999
into `_<digits>`, and appends `_2`, `_3`, ... to a rewrite that would collide with another name of the same kind.
Only the `name` strings of nodes, meshes, materials, animations and scenes change (never vertices, indices,
materials' values or animation channels) and the GLB is re-encoded like `glb_ground.mjs` does.

```bash
node scripts/glb_names.mjs --in asset.glb --out asset.fixed.glb   # print {"renamed": N}
node scripts/glb_names.mjs --check runs/imp/distill/*/asset.glb   # list the files that would change (read only)
```

`--check` prints one `{"file", "renamed"}` line per file that would change (15 of the 540 here) and never writes.
The generator runs the sanitizer on the grounded copy of every attempt and records `renamed_names` per attempt in
`result.json`, so a GLB it writes imports into Blender. The 15 existing files were not rewritten. GLBs exported by
hand from the v1 page can still carry such names, so the v2 prompt should say "never put decimal numbers in names".
